# Практическая работа Q16 на MacBook Air M2

План для Васильева Павла Александровича, вариант 4, на MacBook Air M2 с 8 ГБ оперативной памяти. Работа создаёт lakehouse с тремя слоями, проверяет ответ Q16, сравнивает GZIP и ZSTD и показывает чтение Bronze через Spark. Масштаб всей практической — SF1.

Работа выполнена на SF1. [Заполненный отчёт](отчет.md) содержит фактические количества строк, размеры файлов, замеры GZIP/ZSTD, результаты восстановления и чтения через Spark. Подтверждения сохранены в `artifacts`. Команды ниже позволяют воспроизвести работу на первоначально пустом стенде.

В репозитории оставлены:

- `отчет.md` — заполненный отчёт с шестью скриншотами.
- `compose.yaml`, `.env`, `catalog/` — развёртывание и настройки сервисов.
- `sql/` — готовые запросы для SF1; `scripts/` и `spark/` — подготовка, проверки и чтение Bronze.
- `artifacts/sf1/` — фактические результаты, размеры, измерения и проверка снимков.
- `artifacts/screenshots/`, `services.txt` и `console_excerpt.txt` — подтверждения выполненных действий.

JAR скачиваются отдельной командой, данные lakehouse создаются в Docker-томах. Служебный эталон Q16 для сравнения со Spark создаётся командой `tools verify` и не хранится в Git.

## 1 Требования практической

Основа плана — присланная форма `отчет.md` и описание Q16 из `варианты.md`. Репозитории лабораторных используются как справочные материалы. Презентация объясняет дополнительный бенчмарк Spark с 22 запросами. Её числовые результаты относятся к примеру на другом стенде.

Нужно выполнить следующее:

1. Поднять объектное хранилище, PostgreSQL, Lakekeeper и Trino.
2. Сохранить нужные таблицы TPC-H в Bronze.
3. Построить Silver и Gold, объяснив решения по колонкам, формату, сжатию и партициям.
4. Сравнить результат Gold с исходным Q16.
5. Измерить размер Bronze и время Q16 при GZIP и ZSTD.
6. Показать изменение схемы Silver и восстановление данных по снапшоту.
7. Запустить один дополнительный инструмент в Docker и прочитать через него Bronze. В этом комплекте выбран Spark.
8. Заполнить отчёт и разместить работу в своём репозитории GitHub.

Полный запуск 22 запросов с 1 и 10 потоками из презентации можно выполнить дополнительно, если это отдельно требуется преподавателем. В присланной форме практической обязательная проверка производительности относится к назначенному запросу Q16 и двум кодекам.

## 2 Как устроен стенд

| Компонент | Его роль | Причина выбора |
|---|---|---|
| Silo, совместимый форк MinIO | Хранит файлы Parquet и метаданные Iceberg в бакетах bronze, silver, gold | S3 API и локальный запуск. Этот форк используется в справочном гайде и актуальном примере Lakekeeper |
| PostgreSQL 17 | Хранит служебные данные Lakekeeper | Надёжное транзакционное хранилище метаданных каталога |
| Lakekeeper 0.14.0 | Регистрирует таблицы и предоставляет Iceberg REST API | Общий каталог для Trino и Spark |
| Trino 476 | Генерирует TPC-H, выполняет SQL, записывает слои | Один SQL-движок для источника и обработки, без отдельного скачивания датасета |
| Spark 3.5.3 и Iceberg 1.7.1 | Читает тот же Bronze через REST-каталог и S3 | Показывает совместное использование lakehouse несколькими движками |
| DBeaver Community | Позволяет смотреть таблицы и выполнять SQL с macOS | Удобный SQL-редактор для проверки и скриншотов |

Parquet — формат файлов с данными. Iceberg — табличный формат: он описывает, какие файлы принадлежат таблице, управляет снапшотами и изменениями схемы. Lakekeeper предоставляет доступ к каталогу этих таблиц. PostgreSQL в этой работе хранит служебные данные каталога, а таблицы TPC-H физически лежат в объектном хранилище.

Путь данных: коннектор Trino `tpch` генерирует строки, Trino записывает их в Bronze, затем создаёт Silver и Gold. Trino и Spark запрашивают каталог Lakekeeper и читают файлы из Silo.

В интерфейсах на Mac используются адреса `localhost`. Внутри Docker сервисы обращаются друг к другу по именам `minio`, `lakekeeper`, `postgres`, `trino`. Например, `http://minio:9000` работает из контейнера, а консоль на Mac открывается по `http://localhost:9001`.

## 3 Масштаб и память

SF — scale factor, коэффициент объёма TPC-H. Он увеличивает число строк в больших таблицах. Размер сжатых Parquet-файлов зависит от колонок и кодека.

Для Q16 нужны только три таблицы:

| Масштаб | part | partsupp | supplier |
|---|---:|---:|---:|
| SF1 | 200 000 | 800 000 | 10 000 |

SF1 выбран для Air M2 с 8 ГБ, чтобы оставить память macOS и выполнить все пункты практической. Для отчёта важны воспроизводимость и успешное прохождение проверок.

В Docker Desktop выдели примерно **4 ГБ RAM и 4 CPU**. Это стартовая настройка, которую нужно оценить по фактическому давлению памяти. В комплекте Trino ограничен 2 ГБ памяти контейнера. Spark тоже ограничен 2 ГБ, при этом его driver heap составляет 1 ГБ. Контейнерный лимит включает память сверх Java heap. При запуске Spark мы временно останавливаем Trino. PostgreSQL, Lakekeeper и объектное хранилище остаются запущены.

Освободи ориентировочно 10–15 ГБ диска для образов, библиотек, нескольких копий таблиц и результатов. Это запас для рабочего окружения, а не предсказанный размер Bronze. Docker может использовать больше места из-за кэша образов и старых файлов Iceberg.

Масштаб задаётся в файле `.env`:

```dotenv
LAB_SCALE=sf1
```

SQL-файлы уже настроены на SF1 и создают схемы `bronze.sf1`, `silver.sf1`, `gold.sf1`. Результаты сохраняются в `artifacts/sf1`. Вспомогательные скрипты проверяют, что указан именно SF1.

## 4 Установка на macOS

5. Дождись, пока Docker Engine запустится.
6. В Settings, Resources, Advanced установи примерно 4 ГБ RAM и 4 CPU, затем примени настройки. Если интерфейс новой версии отличается, найди настройки ресурсов виртуальной машины.

```bash
docker run --rm hello-world
```

Последняя команда должна вывести `Hello from Docker!`. Compose входит в Docker Desktop и запускается как `docker compose`, с пробелом.

1. Открой [страницу скачивания DBeaver](https://dbeaver.io/download/).
2. В разделе macOS выбери **Apple Silicon DMG**.
3. Перенеси приложение в Applications и запусти.

Для предложенного способа работы Java, Python, Spark и PostgreSQL отдельно в macOS устанавливать не нужно. Серверные компоненты и Python для вспомогательных команд запускаются в контейнерах. Стандартная сборка DBeaver включает Java.

```bash

```

Если macOS предложит установить инструменты разработчика, согласись. Можно вызвать установку явно:

## 6 Запуск сервисов

Сначала скачай образы основных сервисов:

```bash

```

Затем проверь наличие готовых SQL для SF1 и настройку масштаба из `.env`. При первом запуске дополнительно скачается небольшой образ Python:

```bash
docker compose run --rm tools prepare
```

Запусти хранилище, PostgreSQL и Lakekeeper:

```bash
docker compose up -d minio postgres lakekeeper

```

Compose создаёт сеть. Контейнер `minio-init` создаёт три бакета. Контейнер `migrate` создаёт служебные таблицы в PostgreSQL. Они выполняют одноразовую работу и должны завершиться с `Exited (0)`. Постоянные сервисы продолжают работать.

Теперь инициализируй каталог и зарегистрируй три warehouse:

```bash
docker compose run --rm tools init
```

Команда принимает условия использования Lakekeeper для локального стенда и создаёт `bronze`, `silver`, `gold`. В регистрации у каждого warehouse указан соответствующий бакет, S3 endpoint `http://minio:9000`, регион `us-east-1` и локальные демонстрационные ключи.

Запусти Trino после регистрации warehouse:

```bash
docker compose up -d trino
```

Подожди около полуминуты и проверь:

```bash
curl -f http://localhost:8181/health
curl -f http://localhost:8080/v1/info
docker compose exec -T trino trino --execute 'SHOW CATALOGS'
```

В ответе Trino `starting` должен стать `false`. В списке каталогов должны быть `bronze`, `silver`, `gold`, `tpch`, `system`.

Открой [консоль хранилища](http://localhost:9001). Логин и пароль: `minioadmin` / `minioadmin`. Посмотри бакеты `bronze`, `silver`, `gold`. [Trino UI](http://localhost:8080) принимает любое имя пользователя, например `pavel`, без пароля в этой локальной конфигурации.

## 8 Логика варианта Q16

Q16 считает число разных поставщиков для каждой комбинации бренда, типа и размера детали. Он исключает Brand#45, типы с префиксом MEDIUM POLISHED и поставщиков, у которых комментарий содержит Customer, а затем Complaints. Размер входит в заданный список восьми значений.

| Таблица | Колонки для Q16 | Использование |
|---|---|---|
| part | partkey, brand, type, size | Джойн по partkey, фильтры по бренду, типу и размеру, группировка |
| partsupp | partkey, suppkey | Связь деталей и поставщиков, count DISTINCT suppkey |
| supplier | suppkey, comment | Подзапрос исключает поставщиков с жалобами |

В коннекторе Trino `tpch` имена колонок без префиксов `p_`, `ps_`, `s_`. Запросы из полной лабораторной Spark используют другой набор имён, поэтому смешивать их со схемой этой практической нельзя.

`COUNT(DISTINCT suppkey)` важен: один поставщик может поставлять несколько деталей одной группы. Обычный `COUNT(*)` посчитает связи поставщика с деталями.

## 9 Создание Bronze

Выполни:

```bash
docker compose exec -T trino trino --file /work/sql/01_bronze.sql
```

Скрипт создаёт схемы трёх слоёв и сохраняет полные таблицы `part`, `partsupp`, `supplier` из генератора `tpch.sf1` в `bronze.sf1`. Формат — Parquet, сжатие — ZSTD, партиционирование не задано.

Bronze хранит все исходные колонки. Это удобный учебный выбор: исходные строки доступны для проверки и для новых запросов. В Silver остаются только поля, необходимые Q16. Формой отчёта также допускается оставить в Bronze только нужные колонки, но здесь выбран полный исходный набор трёх таблиц.

Ожидаемые проверки SF1:

```sql
SELECT count(*) FROM bronze.sf1.part;       -- 200000
SELECT count(*) FROM bronze.sf1.partsupp;   -- 800000
SELECT count(*) FROM bronze.sf1.supplier;   -- 10000
```

Это контрольные значения масштаба. В отчёт перенеси значения, которые действительно вернул твой запуск.

В консоли хранилища теперь появятся объекты в бакете Bronze. Lakekeeper создаёт служебные пути с идентификаторами, поэтому имя папки может отличаться от имени SQL-таблицы. Посмотри файлы данных и каталог metadata.

Повторный запуск CREATE TABLE для уже созданной таблицы выдаст ошибку. При частично выполненном скрипте проверь `SHOW TABLES IN bronze.sf1` и выполни в DBeaver только недостающие команды. Не запускай очистку томов для исправления такой ошибки.

## 10 Создание Silver и Gold

Выполни:

```bash
docker compose exec -T trino trino --file /work/sql/02_silver_gold.sql
```

Silver — таблица `silver.sf1.part_supplier_clean`. Она содержит `partkey`, `suppkey`, `brand`, `type`, `size`. Trino соединяет детали с поставками, применяет все условия Q16 и исключает поставщиков с жалобами. Одна строка соответствует подходящей паре детали и поставщика.

На детерминированных данных TPC-H очищение состоит прежде всего в проверке ключей, уменьшении числа колонок и подготовке среза для запроса. Специально добавлять ошибочные строки в основной Bronze не нужно. SCD Type 2 из примера с магазинами не требуется для решения Q16.

Gold — `gold.sf1.q16_supplier_counts`. Он содержит `brand`, `type`, `size`, `supplier_cnt`. Это агрегированный ответ на Q16. Gold строится из Silver, а Silver из Bronze.

Во всех слоях используются Parquet и ZSTD. Parquet удобен для аналитического чтения отдельных колонок. ZSTD выбран как стартовый кодек, а его фактический эффект проверяется в эксперименте. При SF1 у Q16 нет фильтра по дате, и разбиение на множество партиций не даёт очевидной пользы. Поэтому в основном решении партиционирования нет. Это решение нужно объяснить в отчёте, а не считать универсальным правилом для больших объёмов.

Посмотри Gold в DBeaver:

```sql
SELECT * FROM gold.sf1.q16_supplier_counts
ORDER BY supplier_cnt DESC, brand, type, size;
```

Порядок строк не является свойством хранения таблицы. Если нужен отсортированный вывод, всегда указывай ORDER BY при чтении.

Проверь качество и правильность результата:

```bash
docker compose exec -T trino trino --file /work/sql/05_quality.sql
docker compose run --rm tools verify
```

SQL-проверки должны показать ноль NULL-ключей, ноль повторяющихся пар и ноль нарушенных ссылок. Вспомогательная команда сравнивает все строки Gold с исходным Q16 на `tpch.sf1` и сохраняет результаты в `artifacts/sf1/verification.json`, `q16_expected.json`, `q16_gold.csv`.

## 11 Число строк и размер файлов

Выполни:

```bash
docker compose exec -T trino trino --file /work/sql/04_measurements.sql
```

Скрипт показывает размеры активных файлов каждой основной таблицы, число записей в этих файлах, фактические COUNT для Silver и Gold, DDL Silver и статистику.

Для отдельной таблицы:

```sql
SELECT count(*) AS files,
       sum(file_size_in_bytes) AS bytes,
       CAST(sum(file_size_in_bytes) AS DOUBLE) / 1048576.0 AS data_mib
FROM bronze.sf1."partsupp$files"
WHERE content = 0;
```

`$files` показывает файлы текущего снапшота. `content = 0` выбирает файлы данных. Деление на 1 048 576 даёт **MiB**, на 1 000 000 — **MB**. В отчёте подпиши используемую единицу, даже если заголовок шаблона говорит «МБ».

Эта сумма не включает манифесты, JSON-метаданные и старые снапшоты. Размер всего бакета может быть больше, особенно после экспериментов и удаления строк. `SHOW STATS` полезен для статистик оптимизатора, но не заменяет измерение физического размера Parquet-файлов.

## 12 Сравнение GZIP и ZSTD

Создай две независимые копии исходных трёх таблиц:

```bash
docker compose exec -T trino trino --file /work/sql/03_compression.sql
```

Для SF1 получатся схемы `bronze.sf1_gzip` и `bronze.sf1_zstd`. Обе содержат одинаковые строки и колонки из `tpch.sf1`; формат и отсутствие партиционирования одинаковы. Основные таблицы `bronze.sf1` сохраняются. Эти копии реализуют пересоздание Bronze с разными кодеками для эксперимента без удаления основного результата.

Для Trino 476 кодек задаётся перед CREATE TABLE в **той же сессии**:

```sql
SET SESSION bronze.compression_codec = 'GZIP';
CREATE TABLE bronze.sf1_gzip.part
WITH (format = 'PARQUET')
AS SELECT * FROM tpch.sf1.part;
```

В файле SQL эти команды выполняются одним вызовом Trino CLI. Настройка сессии влияет на запись файлов. Она не перекодирует уже существующие файлы. Если в DBeaver выполняешь отдельные блоки, используй одно подключение и выполняй SET непосредственно перед записью.

Теперь измерь Q16:

```bash
docker compose run --rm tools benchmark --repeats 5
```

Команда сначала делает по два прогрева каждого кодека, затем пять измеряемых запусков на каждый кодек. Порядок GZIP/ZSTD чередуется. Каждый раз выполняется полный Q16 напрямую по соответствующему Bronze и проверяется совпадение ответа с эталоном. Время измеряется до получения всех строк результата.

Появятся:

| Файл в artifacts/sf1 | Содержимое |
|---|---|
| benchmark_runs.csv | Все десять измеряемых запусков, ID запроса, время клиентского запроса и время Trino, если сервер вернул его |
| benchmark_summary.csv | Медиана, минимум, максимум и суммарный размер активных файлов трёх таблиц для каждого кодека |

В форму отчёта перенеси `median_client_wall_seconds` и `active_data_mib`. Укажи методику: 2 прогрева, 5 измеряемых повторов, одна машина, один масштаб, одинаковые таблицы, формат и партиционирование. Клиентское время включает передачу полного ответа. Серверное `trino_elapsed_ms` — отдельная метрика, их нельзя смешивать в одной колонке сравнения.

Во время замеров не запускай Spark, не меняй лимиты Docker и подключи ноутбук к питанию. Дай Air остыть после длительной загрузки данных. Если разброс времени сравним с разницей кодеков, вывод должен быть осторожным: на данном объёме устойчивое преимущество по скорости не установлено. Размер файлов при этом можно сравнить отдельно.

Чтение уже готового Gold не подходит для этого эксперимента: оно не читает файлы Bronze. Не меняй SF одновременно с кодеком.

## 13 Изменение схемы и восстановление

Выполни:

```bash
docker compose run --rm tools snapshots
```

Команда создаёт отдельную небольшую демонстрационную таблицу в Silver. Основная таблица Silver остаётся источником Gold. Демонстрация делает следующее:

1. Копирует до 20 строк Silver в таблицу с уникальным именем.
2. Добавляет nullable-колонку `note VARCHAR`.
3. Переименовывает её в `source_note` и проверяет NULL у старых строк.
4. Сохраняет реальный ID снапшота.
5. Удаляет строки из демонстрационной таблицы и проверяет нулевой COUNT.
6. Читает старые строки через `FOR VERSION AS OF`.
7. Возвращает текущие данные к сохранённому снапшоту и проверяет восстановленный COUNT.

В `artifacts/sf1/snapshot_demo.json` будут реальные имя таблицы, ID и результаты COUNT. В `restore_snapshot.sql` появится исполняемая команда восстановления с ID именно твоего запуска.

Шаблон синтаксиса Trino 476:

```sql
-- Вставь настоящие имя и ID из snapshot_demo.json:
SELECT * FROM silver.sf1.snapshot_demo_ИМЯ FOR VERSION AS OF ID;
ALTER TABLE silver.sf1.snapshot_demo_ИМЯ EXECUTE rollback_to_snapshot(ID);
```

Не выполняй этот шаблон с буквами ИМЯ/ID. Готовая конкретная команда находится в сгенерированном `restore_snapshot.sql`.

Для объяснения schema evolution: новая nullable-колонка доступна без обязательной перезаписи всех старых файлов, у прежних строк она NULL. Iceberg отслеживает поля по идентификаторам, поэтому переименование не обязано переписывать данные. Для объяснения time travel: старый снапшот хранит ссылку на прежний набор файлов. Он должен существовать, и соответствующие файлы должны быть сохранены. Откат снапшота данных не следует описывать как полное восстановление всех прошлых изменений схемы.

## 14 Чтение Bronze через Spark

Скачай две библиотеки Iceberg:

```bash
bash scripts/download_jars.sh
```

Они добавляют поддержку Iceberg и S3 к Spark 3.5.3. Файлы монтируются в `/opt/spark/iceberg-jars`, отдельно от штатного каталога библиотек Spark.

На Air с 8 ГБ временно останови Trino и запусти Spark:

```bash
docker compose stop trino
docker compose run --rm spark
```

Если хочешь сохранить весь вывод, вместо второй команды используй:

```bash
set -o pipefail
docker compose run --rm spark 2>&1 | tee artifacts/spark.log
```

Spark обращается к Lakekeeper и S3 непосредственно, поэтому остановленный Trino ему не мешает. В конфигурации Spark выбран REST-каталог Bronze, а не каталог `bench` из полной лабораторной.

Скрипт проверяет COUNT трёх таблиц, показывает десять деталей, выполняет Q16 по **Bronze** и сохраняет `artifacts/sf1/spark_q16.csv` и `spark_summary.json`. Если перед этим выполнен `tools verify`, Spark также сравнит все строки со сохранённым результатом Trino. В summary должно быть `matches_trino: true`.

Это закрывает пункт формы «один инструмент в Docker и взаимодействие с Bronze». Отдельный BI-сервис для этого выбранного пути не нужен. DBeaver остаётся SQL-клиентом на Mac; он не заменяет выбранный в этом пункте Docker-инструмент Spark.

После выполнения снова запусти Trino:

```bash
docker compose start trino
```

Время Q16 в `spark_summary.json` не включает старт JVM и SparkSession. Это один запуск после чтения контрольных таблиц. Для строгого сравнения скорости Trino и Spark нужны одинаковая методика прогрева и повторов и сопоставимые лимиты ресурсов. В основной практической этот шаг подтверждает совместимость и доступ к Bronze.

## 15 Контроль памяти на ноутбуке

Открой Activity Monitor, вкладку Memory. Во время нагрузки смотри на Memory Pressure. Продолжительное высокое давление памяти, растущий swap вместе с торможением приложений или ошибки памяти означают, что текущая параллельная нагрузка слишком тяжёлая.

Для этой практической масштаб остаётся SF1. Закрой ненужные тяжёлые приложения и выполняй этапы последовательно. Перед Spark останови Trino. Во время сравнения GZIP и ZSTD оставляй одинаковые настройки ресурсов и не запускай другие вычислительные задачи.

У полной лабораторной восемь таблиц, включая примерно 6 млн строк lineitem уже на SF1, и существенно более сложная нагрузка, чем у Q16. Её режим 10 потоков не нужен для основного пути этой практической.

## 18 Повторный запуск и остановка

Чтобы остановить сервисы и сохранить тома:

```bash
docker compose stop
```

Чтобы продолжить уже созданный стенд:

```bash
docker compose start minio postgres lakekeeper trino
```

После рестарта дождись готовности Lakekeeper и Trino. SQL создания таблиц повторять не нужно.

## 19 Типичные ошибки

| Ошибка | Как исправить |
|---|---|
| Cannot connect to the Docker daemon | Запусти Docker Desktop и дождись готовности Engine |
| Port is already allocated | Проверь слушающий процесс и останови прежний стенд на этом порту |
| Container migrate завершился с ненулевым кодом | Посмотри `docker compose logs migrate postgres`, проверь готовность PostgreSQL |
| Lakekeeper не готов | Посмотри health и логи, убедись, что minio-init и migrate завершились успешно |
| Catalog tpch/bronze does not exist | Проверь файлы catalog и перезапусти Trino |
| Table already exists | Покажи список таблиц и выполни только недостающие шаги |
| Неизвестное свойство compression_codec в WITH | Используй SET SESSION bronze.compression_codec перед записью |
| Unknown configuration property fs.s3.enabled | Для закреплённого Trino 476 требуется fs.native-s3.enabled; не заменяй его строками из документации другой версии |
| Query exceeded memory limit | Проверь масштаб, останови параллельную нагрузку, начни с SF1 |
| Java heap space у Spark | Останови Trino, проверь heap и общий лимит. Не увеличивай их одновременно до объёма всей RAM Mac |
| IcebergSparkSessionExtensions class not found | Проверь оба JAR и путь spark.jars |
| Cannot connect to minio/lakekeeper | Spark должен запускаться через этот Compose, в его общей сети |
| No matching manifest for linux/arm64 | Проверь, какой образ не поддерживает ARM. Можно задать `platform: linux/amd64` только этому сервису, но результаты тогда включают влияние эмуляции |
| Spark не совпал с Trino | Проверь масштаб, source-схему и q16_expected.json. Не переноси такой результат в отчёт как успешный |

## 20 Дополнительная лабораторная Spark

Если отдельно нужно повторить презентацию с 22 запросами, используй [инструкцию лабораторной Spark](https://github.com/m1705161/laba2/blob/main/tpch-spark/README.md) как самостоятельный дополнительный эксперимент:

1. Создай отдельный бакет и warehouse `bench`, добавь его каталог Trino.
2. Материализуй все восемь таблиц. В копии `materialize_sf5.sql` замени все источники `tpch.sf5` на `tpch.sf1` и назови свою копию `materialize_sf1.sql`.
3. Сохрани предусмотренные скриптом имена колонок с префиксами. Они нужны для 22 SQL из лабораторной.
4. Настрой Spark на REST-каталог `bench`, общий S3 и совместимые JAR.
5. На Air с 8 ГБ сначала выполни 1 поток, остановив Trino после материализации. 22 запроса — существенно тяжелее текущего Q16.
6. Режим 10 потоков выполняй только после устойчивого базового прогона и оценки памяти. Он делит ресурсы одной машины и не означает десять отдельных Spark-кластеров. Если преподаватель требует 10 потоков, для этого ноутбука разумно рассмотреть более мощный стенд.
7. Сохрани разные CSV для каждого режима. Успешных исполнений должно быть 22 и 220 соответственно. Ошибки нужно отразить отдельно. Для полезной пропускной способности дели число успешных запросов на общее время серии, а не включай ошибки в число обработанных запросов.

Это учебный прогон запросов TPC-H. Его результаты не следует выдавать за официально сертифицированные метрики TPC-H. Время 136/2197 секунд из презентации не является ожидаемым результатом твоего Mac.
